## 1. 사용자 입력

````text
너가 제시한 번호랑 엑셀 행 번호가 달라서 보기가 불편해. 그리고 adp랑 redhat이랑 똑같은 거 맞아? 엑셀 8행을 보니까 너가 redhat이라고 한 거랑 adp 값이 달라
````

**답변 요약**: 번호는 CSV의 `no`(1~30)이고 엑셀 행 = 번호 + 1이라고 설명하고, 앞으로 "엑셀 N행"으로 말하기로 했다(유형 A/B/C 번호도 엑셀 행으로 바꿔 보여 줌). ADP는 CVE 레코드에 올라온 보강 정보 전체이고 Red Hat(`redhat-SADP`)은 그 제공자 중 하나라서 같은 것이 아니라고 답했다.

````text

````

**답변 요약**: 엑셀 8~31행을 행마다 CVE, 제품, 제목, KEV·CNA·ADP 값, 쟁점, 참고 의견으로 설명했다. 제 의견은 확정이 아니며 일부 CVE 내용은 일반 지식이라 원문 확인이 아니라고 밝혔다. 쓰지 말라는(Discouraged) 상위 항목은 CWE-20, 119, 287, 345, 138이라고 정리했다.

````text
* NIST SP 800-53: 구체적인 보안 통제
* NIST SP 800-61: 침해사고 대응 지침

현재 RootCause 각각에 대해 CWE, NIST CSF, NIST 800-53을 연결하는 매핑표를 작성하라.
주의사항:

* 실제 대응 관계가 없는 CWE를 억지로 연결하지 말 것.
* NIST CSF의 기능 및 세부 범주를 정확하게 구분할 것.
* NIST 800-53의 통제 패밀리와 개별 통제 ID를 구분할 것.
* 제시하는 표준 번호와 명칭이 실제 공식 문서에 존재하는지 검증할 것.

B3. ActorOrigin의 경계 규칙
현재 ActorOrigin 분류와 README의 ACTOR_ORIGIN_BOUNDARY_EXAMPLES 6개를 검토하라.
특히 다음 사항을 판단하라.

1. FORMER_INSIDER를 별도 분류로 유지하는 것이 적절한가?
2. 공격 시점의 고용 상태를 기준으로 하는 것이 타당한가?
3. 전직 직원이 과거에 취득한 인증키나 정보를 이용한 경우 어떻게 분류해야 하는가?
4. 퇴사 예정이지만 아직 재직 중인 직원은 어떻게 분류해야 하는가?
5. 협력사 직원과 외부 공격자가 협력사 계정을 도용한 경우를 구분할 수 있는가?
6. 공격자 신원과 계정 소유자를 별도로 관리해야 하는가?

다음 분류의 정의를 검토하고 필요한 경우 수정하라.

* INTERNAL
* FORMER_INSIDER
* PARTNER
* EXTERNAL

특히 FORMER_INSIDER는 단순히 과거에 조직에 근무했다는 이유만으로 부여해서는 안 된다.
공격 시점의 고용 상태와 과거 조직 관계에서 취득한 권한·정보·접근 수단이 공격에 사용되었는지를 구분하라.
또한 VERIS 등 외부 분류 체계와의 대응 관계가 있다면 공식 정의를 확인하라.
B4. 질문 틀 (a)(b)(c)의 적절성
README 첫 부분의 사건 분석 질문 틀을 검토하라.
현재 질문 구조:
(a) 취약점(Vulnerability)
(b) 약점 및 관리 실패(Weakness / RootCause)
(c) 공격 기법(Attack Technique)
다음 사항을 판단하라.

1. 세 가지 질문이 침해사고 분석 목적에 적합한가?
2. CVE, CWE, NIST, ATT&CK의 역할이 명확하게 구분되는가?
3. 취약점과 RootCause가 중복 집계될 가능성은 없는가?
4. 공격자가 수행한 행동과 공격을 가능하게 한 관리 실패를 명확하게 구분할 수 있는가?
5. ActorOrigin, ThreatActor, 피해 자산을 별도로 유지하는 것이 적절한가?
6. 확인되지 않은 정보와 출처에 언급되지 않은 정보를 구분할 필요가 있는가?

* answered
* not_confirmed
* not_mentioned_in_sources
* not_applicable
* not_assessed

각 상태의 의미와 사용 조건을 명확하게 정의하라.
최종적으로 기존 질문 틀을 유지할지, 수정할지 결정하고 실제 사건 분석에 사용할 권장 질문 문장을 작성하라.
B5. AI 기반 MITRE ATT&CK 매핑의 검증 체계
현재 attack_mapping.py와 README의 '기법 층'을 직접 분석하라.
특히 다음 기능과 로직을 확인하라.

* ATT&CK 후보 제안
* ATT&CK ID 유효성 검사
* 상위 기법과 하위 기법 선택
* no_match 처리
* documented 처리
* malware 기반 기법 추론
* confidence 수준
* 사람의 검토 및 확정 처리

다음 원칙을 기준으로 검토하라.
AI는 ATT&CK 후보를 제안할 수 있지만, 사람이 검증하기 전까지 확정된 기법으로 집계해서는 안 된다.
검토할 내용:

1. AI가 제안한 기법을 누가 확인해야 하는가?
2. 1차 분석가와 2차 검토자의 역할을 구분할 필요가 있는가?
3. ATT&CK 기법의 정의와 실제 공격 행동이 일치하는지 어떤 기준으로 검증할 것인가?
4. 하위 기법을 선택할 때 필요한 증거는 무엇인가?
5. AI confidence와 실제 증거의 강도를 분리해야 하는가?
6. 문서에서 기법을 직접 언급한 것과 실제 공격에 사용된 것이 확인된 것을 구분하고 있는가?
7. 악성코드의 알려진 기능을 해당 사건에서 실제 실행된 공격 기법으로 잘못 집계할 가능성은 없는가?
8. ATT&CK 버전 변경과 기법 폐기·변경 이력을 관리할 필요가 있는가?

특히 다음 코드 패턴을 집중적으로 검토하라.

* documented 항목을 무조건 counted=True로 처리하는 로직
* specific Boolean에 의존하는 하위 기법 검증
* confidence와 evidence strength의 구분
* 동일 기법이 여러 출처에서 다른 확정 수준으로 등장할 때의 처리
* derive_from_malware()의 집계 방식

실제 코드에 문제가 있다면 문제가 발생하는 조건과 수정 방안을 제시하라.
권장 검증 상태는 다음을 기준으로 검토하라.

* ai_suggested
* human_confirmed
* human_rejected
* no_match
* documented

단, documented와 human_confirmed는 서로 다른 개념이므로 별도 관리하는 것이 적절한지 판단하라.
3. 종합적인 데이터 모델 개선
B1~B5의 검토 결과를 종합하여 최종적인 지식 그래프 구조를 제안하라.
다음과 같은 분석 계층을 고려하라.

1. Incident Facts: 사건에서 확인된 사실과 출처
2. Vulnerability: CVE 등 악용된 취약점
3. Weakness / RootCause: 기술적 약점 및 조직적 관리 실패
4. AttackBehavior: 문서에서 확인된 공격 행동
5. ATT&CK Technique: 공격 행동에 대한 표준 매핑
6. ActorOrigin: 공격자의 조직적 관계
7. Asset: 피해를 입은 시스템 및 정보 자산

각 계층 사이의 관계를 정의하라.
특히 다음 관계를 구분하라.

* 취약점이 공격에 악용됨
* 보안 통제 실패가 공격을 가능하게 함
* 공격자가 특정 행동을 수행함
* 공격 행동이 ATT&CK 기법에 대응됨
* 공격자가 특정 자산에 접근하거나 영향을 미침

중요한 것은 모든 관계를 인과관계로 단정하지 않는 것이다.
출처에서 확인된 관계와 분석가가 추론한 관계를 구분할 수 있는 데이터 모델을 제안하라.
````

````text
## 2. B1. RootCause 시드 8개 검토 결과

### 최종 판단: 기존 8개 유지 + 상위 분류 도입 검토

현재 8개 항목은 초기 침해사고 분류 체계로 적절하다.

| RootCause | 검토 결과 |
|---|---|
| UNPATCHED_KNOWN_VULNERABILITY | 유지 |
| CREDENTIAL_OR_KEY_MISMANAGEMENT | 유지 |
| INSUFFICIENT_ENCRYPTION | 유지 |
| WEAK_ACCESS_CONTROL | 유지 |
| INSUFFICIENT_MONITORING_DETECTION | 유지 |
| INADEQUATE_INCIDENT_RESPONSE | 유지 |
| THIRD_PARTY_OR_SUPPLY_CHAIN_RISK | 유지 |
| MISCONFIGURATION | 유지하되 경계 규칙 명확화 |

### 주요 문제

현재 분류는 동일한 수준의 개념으로 구성되어 있지 않다.

- ENCRYPTION, ACCESS_CONTROL, MONITORING은 기술적 보안 통제의 실패와 밀접하다.
- INCIDENT_RESPONSE는 조직의 사고 대응 절차 실패다.
- UNPATCHED는 기술적 취약점 자체보다는 취약점 관리 및 패치 운영 실패에 해당한다.
- THIRD_PARTY는 외부 의존성 및 공급망 위험 관리 문제다.
- CREDENTIAL은 기술적 인증정보와 조직의 계정·키 수명주기 관리가 혼재한다.

이러한 분류를 그대로 유지하면 사건 간 통계에서 기술적 약점과 조직적 관리 실패가 같은 수준으로 집계되는 문제가 발생할 수 있다.

### 권장 개선

기존 8개를 폐기하거나 무조건 세분화하기보다는 상위 분류를 추가하는 방식을 권장한다.

| 상위 분류 | 포함할 기존 RootCause |
|---|---|
| 기술적 통제 실패 | INSUFFICIENT_ENCRYPTION, WEAK_ACCESS_CONTROL, MISCONFIGURATION |
| 취약점 관리 실패 | UNPATCHED_KNOWN_VULNERABILITY |
| 자산·계정 관리 실패 | CREDENTIAL_OR_KEY_MISMANAGEMENT |
| 보안 운영 실패 | INSUFFICIENT_MONITORING_DETECTION, INADEQUATE_INCIDENT_RESPONSE |
| 외부 의존성 관리 실패 | THIRD_PARTY_OR_SUPPLY_CHAIN_RISK |

추가 후보로 다음 항목을 검토할 수 있다.

- 보안 인식 및 교육 부족
- 백업 및 복구 체계 미흡
- 취약점 식별·평가·우선순위 관리 실패
- 계정 수명주기 관리 실패
- 데이터 거버넌스 미흡
- 네트워크 세분화 및 격리 미흡
- 물리적 보안 통제 미흡

다만 현재 단계에서 이 항목들을 모두 새로운 RootCause로 추가하는 것은 권장하지 않는다.

파일럿에서 기존 8개로 분류할 수 없는 사례를 수집하고, 기존 항목과 독립적인 실패인지 검증한 뒤 추가하는 것이 좋다.

### 기존 경계 규칙

현재 정의한 5개 경계 규칙은 유지하는 것이 좋다.

1. 인증정보·키의 수명주기 실패는 CREDENTIAL, 권한 범위·분리·인증 요구 실패는 WEAK_ACCESS_CONTROL.
2. 자체 시스템의 공개 패치 미적용은 UNPATCHED, 외부 공급사 및 협력사 침해는 THIRD_PARTY.
3. 침입을 인지하지 못한 것은 MONITORING, 인지하고도 대응하지 않은 것은 INCIDENT_RESPONSE.
4. 잘못된 설정·기본값은 MISCONFIGURATION, 통제 자체의 부재는 WEAK_ACCESS_CONTROL.
5. 암호화가 없거나 약하다고 명시된 경우에만 INSUFFICIENT_ENCRYPTION.

특히 결과나 피해 규모만으로 RootCause를 추측하지 않는 원칙을 유지해야 한다.

## 3. B2. 조직 절차 실패와 CWE 대응 결과

### 최종 판단: CWE 유지 + NIST CSF 2.0 및 NIST SP 800-53 추가

조직적 관리 실패를 CWE에 억지로 대응시키는 것은 적절하지 않다.

CWE는 소프트웨어 및 하드웨어의 약점을 분류하는 체계이므로 다음과 같은 문제에는 적합하다.

- 인증 및 인가 구현 오류
- 암호화 구현상의 문제
- 접근 통제 결함
- 메모리 관리 오류
- 입력값 검증 문제

반면 다음은 조직의 보안 운영 및 관리 실패에 해당한다.

- 침해사고 대응 절차 미흡
- 패치 운영 실패
- 퇴직자 인증키 폐기 실패
- 협력사 보안 위험 관리 실패
- 이상 행위 탐지 및 모니터링 실패

### 권장 표준

| 표준 | 역할 |
|---|---|
| CWE | 기술적 약점 분류 |
| NIST CSF 2.0 | 조직의 사이버보안 위험관리 및 통제 영역 분류 |
| NIST SP 800-53 Rev. 5 | 구체적인 보안 통제 카탈로그 |
| NIST SP 800-61 Rev. 3 | 침해사고 대응 지침 |

### RootCause별 매핑 후보

| RootCause | CWE 후보 | NIST CSF 2.0 | NIST 800-53 후보 |
|---|---|---|---|
| UNPATCHED_KNOWN_VULNERABILITY | CWE-1395, CWE-1104 | PR.PS | SI-2 |
| CREDENTIAL_OR_KEY_MISMANAGEMENT | CWE-798, CWE-324 | PR.AA | IA-5, AC-2 |
| INSUFFICIENT_ENCRYPTION | CWE-311, CWE-327, CWE-326 | PR.DS | SC-8, SC-28 |
| WEAK_ACCESS_CONTROL | CWE-862, CWE-863, CWE-306 등 | PR.AA | AC 계열 |
| INSUFFICIENT_MONITORING_DETECTION | CWE-778 | DE.CM, DE.AE | AU 계열 |
| INADEQUATE_INCIDENT_RESPONSE | 직접 대응 CWE 없음 | RS.MA, RS.MI | IR 계열 |
| THIRD_PARTY_OR_SUPPLY_CHAIN_RISK | CWE-1357 등 | GV.SC | SR 계열 |
| MISCONFIGURATION | CWE-1188 등 | PR.PS | CM 계열 |

위 표는 매핑 후보이며 실제 확정 시에는 구체적인 실패 내용과 각 표준의 통제 정의를 대조해야 한다.

특히 CWE의 기존 매핑 사용 구분(Allowed, Allowed-with-Review, Discouraged)을 유지해야 한다. 포괄적인 CWE를 구체적인 약점 대신 무조건 사용하는 것은 피해야 한다.

### 권장 데이터 구조

기존 ROOT_CAUSE_CWE_MAP을 완전히 대체하기보다는 다음과 같이 확장하는 것이 좋다.

```python
ROOT_CAUSE_STANDARD_MAP = {
    "INADEQUATE_INCIDENT_RESPONSE": {
        "cwe": [],
        "nist_csf": ["RS.MA", "RS.MI"],
        "nist_800_53": ["IR"],
    }
}
```

실제 구현에서는 NIST 800-53의 통제 패밀리와 개별 통제 ID를 구분해 관리한다.

표준 간 역할을 명확히 구분하는 것이 핵심이다.

## 4. B3. ActorOrigin 경계 검토 결과

### 최종 판단: FORMER_INSIDER 유지 + 정의 및 경계 사례 보완

현재 4개 분류는 유지하는 것이 좋다.

- INTERNAL
- FORMER_INSIDER
- PARTNER
- EXTERNAL

특히 FORMER_INSIDER를 별도 값으로 유지하는 결정은 적절하다.

VERIS에서는 전직 직원을 External로 분류하는 대응 관계를 유지하되, 프로젝트 내부에서는 전직자의 과거 조직 관계를 보존하는 것이 사건 분석에 더 유용하다.

### 공격 시점의 고용 상태 기준

현재 원칙인 공격(접근)이 발생한 시점의 고용 상태를 기준으로 하는 방식은 타당하다.

| 상황 | 분류 |
|---|---|
| 퇴사 후 남아 있던 인증키로 접근 | FORMER_INSIDER |
| 재직 중 퇴사 직전에 데이터 복사 | INTERNAL |
| 퇴사 의사를 밝혔지만 재직 중 권한 오용 | INTERNAL |
| 실제 협력사 직원이 정당한 업무 관계에서 접근해 악용 | PARTNER |
| 외부 해킹 조직의 침입 | EXTERNAL |
| 고용 상태 및 접근 시점을 확인할 수 없음 | 기록하지 않음 |

### 수정이 필요한 사례

기존 경계 사례 중 '협력사 직원의 계정이 도용되어 침입에 쓰였다'는 사례는 수정이 필요하다.

계정 소유자가 협력사 직원이라고 해서 실제 공격자까지 PARTNER로 분류해서는 안 된다.

다음 두 가지를 구분해야 한다.

- 협력사 직원 본인이 공격을 수행한 경우: PARTNER
- 외부 공격자가 협력사 직원의 계정을 탈취한 경우: EXTERNAL 또는 공격자 유형 미확인

따라서 공격자 신원과 계정 소유자는 별도 개념으로 관리하는 것이 좋다.

### 권장 정의

| 값 | 정의 |
|---|---|
| INTERNAL | 공격 시점에 피해 조직의 직원 또는 계약자 신분인 행위자 |
| FORMER_INSIDER | 공격 시점에는 퇴직·계약 종료 상태이며, 과거 조직 관계에서 취득한 권한·정보·접근 수단을 이용한 행위자 |
| PARTNER | 협력사·공급사 등 외부 조직과의 정당한 업무 관계를 통해 접근한 행위자 |
| EXTERNAL | 피해 조직과 직접적인 정당한 업무 관계가 없는 행위자 |

전직자라는 사실만으로 FORMER_INSIDER를 부여하지 않는다. 과거 조직 관계와 공격의 연관성이 확인되어야 한다.

기존의 UNKNOWN 미사용 및 미언급 상태로 관리하는 원칙은 유지한다.

## 5. B4. 질문 틀 검토 결과

### 최종 판단: 기존 (a)(b)(c) 구조 유지 + 정의 보완

현재 질문 틀은 침해사고 분석 목적에 적합하다.

(a) 취약점(Vulnerability)
(b) 약점 및 관리 실패(Weakness / RootCause)
(c) 공격 행동 및 기법(AttackBehavior / ATT&CK Technique)

세 항목은 서로 다른 분석 수준이므로 구분해야 한다.

| 구분 | 분석 대상 | 표준 |
|---|---|---|
| (a) | 악용된 취약점 | CVE, NVD, KEV |
| (b) | 기술적 약점 및 조직적 관리 실패 | CWE, NIST CSF, NIST 800-53 |
| (c) | 실제 공격 행동 및 기법 | MITRE ATT&CK |

### 중요한 구분

취약점과 RootCause가 같은 사건에서 함께 등장할 수 있지만, 같은 원인을 두 번 집계해서는 안 된다.

예를 들어 알려진 취약점의 패치 미적용 사건이라면 다음과 같이 기록한다.

- (a): 실제 악용된 CVE
- (b): 패치 관리 실패
- (c): 공격자가 수행한 실제 공격 행동

쿠팡 사건처럼 공식 문서에서 특정 CVE가 확인되지 않은 경우에는 임의의 취약점을 생성하지 않고 미언급 또는 미확인으로 처리한다.

### 질문 틀의 권장 수정

사건 X에서 확인된 공격과 관련하여 다음을 분석한다.

(a) 악용된 취약점: 공격에 사용된 것으로 확인된 CVE 등 알려진 취약점은 무엇인가?

(b) 보안 약점 및 관리 실패: 공격을 가능하게 하거나 피해를 확대시킨 기술적 약점과 조직적 통제 실패는 무엇인가?

(c) 공격 행동 및 기법: 공격자가 실제로 수행한 행동은 무엇이며, MITRE ATT&CK의 어떤 기법에 해당하는가?

각 항목에 출처, 출처 유형, 확정·주장·추정 상태를 기록한다. 출처에 없는 사실은 추측하지 않는다.

### slot_state 보완

현재 상태에 다음 두 가지를 추가하는 것을 권장한다.

| 상태 | 의미 |
|---|---|
| answered | 관련 사실 확인 |
| not_confirmed | 관련 정보가 있지만 미확정 |
| not_mentioned_in_sources | 검토한 문서에 해당 정보가 없음 |
| not_applicable | 해당 질문이 사건에 적용되지 않음 |
| not_assessed | 아직 평가하지 않음 |

특히 not_mentioned_in_sources와 not_confirmed를 혼동해서는 안 된다.

## 6. B5. ATT&CK 매핑 검토 결과

### 최종 판단: D5~D8 유지 + 매핑 검증 및 집계 로직 보완

현재 설계의 핵심인 다음 구조는 유지하는 것이 좋다.

1. 문서에서 확인된 공격 행동을 AttackBehavior로 보존한다.
2. AI가 ATT&CK 후보를 제안한다.
3. 사람이 후보의 타당성을 검토하고 승인한다.
4. 이름 있는 악성코드에서 도출한 기법은 문서 직접 확인 및 사람 승인 결과와 구분한다.

AI가 제안한 기법은 사람이 확인하기 전까지 확정 집계하지 않는 D6은 적절하다.

### 검증 책임

| 역할 | 업무 |
|---|---|
| AI | 공격 행동 추출 및 ATT&CK 후보 제안 |
| 1차 보안 분석가 | 행동과 기법 정의의 일치 여부 검토 |
| 2차 보안 분석가 | 중요 사건 및 논쟁적인 매핑 교차 검토 |
| 최종 승인자 | 결과 확정 및 변경 이력 관리 |

초기 파일럿에서는 한 명의 분석가가 모든 후보를 검토하고, 일부 표본을 두 번째 분석가가 독립적으로 검토하는 방식도 가능하다.

### attack_mapping.py에서 개선할 사항

#### ① documented와 confirmed 구분

현재 코드에서 문서가 ATT&CK 기법 이름이나 ID를 직접 언급하면 다음과 같이 처리한다.

```python
"label": "documented",
"counted": True
```

이것은 AI가 제안한 기법을 사람 확인 없이 확정하는 문제와는 별개다.

다만 문서에 기법 이름이 등장했다는 사실과 해당 기법이 실제 공격에 사용되었다는 사실은 구분해야 한다.

현재 `summarize_attack_layer()`의 documented 처리에서는 해당 트리플렛의 `assertion_status`를 반영하지 않는다.

따라서 다음 정보를 별도로 보존하도록 개선하는 것이 좋다.

- 문서가 직접 언급했는지
- 문서에서 확정된 사실인지
- 문서의 주장인지
- 분석가의 추론인지
- 사람이 별도로 검증했는지

문서에서 기법을 언급한 경우에도 해당 주장이 claimed 또는 inferred라면 무조건 확정 집계해서는 안 된다.

#### ② specific Boolean 개선

현재 `validate_candidates()`는 `specific` Boolean을 사용하여 하위 기법을 상위 기법으로 올릴지 결정한다.

그러나 하위 기법의 구체성은 단순한 Boolean보다 실제 증거를 기준으로 판단해야 한다.

권장 개선 항목:

- 근거 문장
- 해당 하위 기법의 필수 조건
- 필수 조건 충족 여부
- 상위 기법보다 하위 기법을 선택한 이유
- 사람의 검토 결과

하위 기법을 유지하려면 실제 행동에 관한 구체적인 근거가 있어야 한다.

#### ③ confidence와 evidence strength 분리

현재 high, medium, low 신뢰도는 AI가 후보를 얼마나 확신하는지 나타낸다.

하지만 이것이 실제 증거의 강도를 의미하지는 않는다.

다음 네 가지를 구분하는 것을 권장한다.

- AI confidence: AI의 후보 확신 수준
- Evidence strength: 출처가 실제 행동을 뒷받침하는 수준
- Mapping validity: ATT&CK 정의와 실제 행동의 일치 여부
- Review status: 사람의 검증 여부

#### ④ 동일 기법의 다중 출처 관리

현재 `documented.setdefault()`는 동일 기법이 여러 출처에서 등장해도 최초 기록만 보존한다.

따라서 출처별 주장을 별도로 보존하고, 각 출처의 확정 수준을 유지해야 한다.

서로 다른 출처가 같은 기법을 다르게 주장하는 경우 입력 순서에 따라 결과가 결정되지 않도록 해야 한다.

#### ⑤ 악성코드 기반 기법 유도

현재 `derive_from_malware()`가 악성코드와 연결된 ATT&CK 기법을 가져오고 `counted=False`로 처리하는 방향은 적절하다.

악성코드의 알려진 기능이 해당 사건에서 실제로 실행되었다고 단정해서는 안 된다.

이 결과는 뼈대 유도 정보로 보존하고, 실제 사건에서 확인된 공격 기법과 분리해야 한다.

#### ⑥ ATT&CK 버전 관리

현재 `BACKBONE_SNAPSHOTS`에 버전을 기록하는 방향은 적절하다.

다만 개별 매핑 기록에도 다음을 보존하는 것이 좋다.

- ATT&CK 버전
- 매핑 날짜
- 검토 날짜
- 검토자
- 기법의 현재 유효성
- 변경 및 재검토 이력

### 권장 검증 상태

| 상태 | 의미 | 확정 집계 |
|---|---|---|
| ai_suggested | AI 후보 | 제외 |
| human_confirmed | 사람 승인 | 포함 |
| human_rejected | 사람 기각 | 제외 |
| no_match | 적합한 기법 없음 | 제외 |
| documented | 문서 직접 언급 | 출처의 assertion_status에 따라 결정 |
| backbone_derived | 악성코드에서 유도 | 별도 집계 |

documented와 human_confirmed는 서로 다른 개념이므로 하나의 상태로 합치지 않는 것이 좋다.

## 7. 종합 데이터 모델 개선 방향

현재 프로젝트의 핵심 구조를 유지하면서 다음과 같이 정리하는 것이 적절하다.

### 분석 계층

1. Incident Facts: 사건의 확인된 사실과 출처
2. Vulnerability: CVE 등 악용된 취약점
3. Weakness / RootCause: 기술적 약점과 조직적 관리 실패
4. AttackBehavior: 문서에서 확인된 공격 행동
5. ATT&CK Technique: 공격 행동과 ATT&CK 기법의 매핑
6. ActorOrigin: 공격자의 조직적 관계
7. Asset: 침해된 시스템 및 정보 자산

### 관계 정의

- EXPLOITED_VULNERABILITY: 취약점이 공격에 악용됨
- EXPLOITED_WEAKNESS: 공격과 관련된 기술적 약점
- HAS_ROOT_CAUSE: 사건에서 확인된 관리 실패
- USED_BEHAVIOR: 공격자가 수행한 행동
- USED_TECHNIQUE: 확인된 공격 기법
- HAS_ACTOR_ORIGIN: 공격자의 조직적 관계
- AFFECTED_ASSET: 영향을 받은 자산

중요한 점은 취약점, 관리 실패, 공격 행동 사이의 관계를 모두 자동으로 인과관계라고 단정하지 않는 것이다.

출처에서 직접 확인된 사실과 분석가가 추론한 관계를 구분해야 한다.

## 9. 최종 결론

현재 프로젝트는 기본적인 설계 방향을 유지하는 것이 좋다.

가장 중요한 것은 새로운 표준이나 분류를 무조건 추가하는 것이 아니라, 각 분류가 무엇을 설명하는지 명확하게 만드는 것이다.

특히 다음 원칙을 프로젝트의 핵심 설계 원칙으로 유지해야 한다.

1. 취약점은 공격에 악용된 기술적 결함을 나타낸다.
2. RootCause는 공격을 가능하게 하거나 피해를 확대시킨 통제 실패를 나타낸다.
3. AttackBehavior는 문서에서 확인된 실제 공격 행동을 보존한다.
4. ATT&CK는 공격 행동을 표준화하여 비교하기 위한 매핑 체계다.
5. AI의 제안과 사람의 검증 결과를 구분한다.
6. 출처에 없는 사실과 확인되지 않은 인과관계는 추측하지 않는다.

프로젝트의 차별점은 뉴스에서 CVE나 ATT&CK ID를 추출하는 데 그치지 않고, 실제 침해사고의 기술적 취약점, 조직적 관리 실패, 공격자의 행동을 연결하여 사건 간 공통 원인과 공격 패턴을 분석하는 데 있다.

따라서 기존 데이터 모델을 유지하면서 B1과 B2의 RootCause 및 표준 매핑을 먼저 개선하고, B5의 ATT&CK 검증 체계를 보완하는 순서로 개발하는 것을 권장한다.
````

````text
# 3. Q2. 상위 분류와 비교 기준의 재설계

## 3.1. 기존 5개 상위 분류의 문제점

기존 상위 분류는 서로 다른 기준이 혼재되어 있다.

- 기술적 통제 실패: 실패의 성격
- 취약점 관리 실패: 관리 업무 영역
- 자산·계정 관리 실패: 관리 대상
- 보안 운영 실패: 업무 기능
- 외부 의존성 관리 실패: 조직적 관리 대상

따라서 이 다섯 가지를 상호 배타적인 비교 기준으로 사용하면 일관성이 떨어진다.

또한 NIST CSF 카테고리와 기존 상위 분류는 서로 다른 목적의 분류이므로 일치하지 않을 수 있다.

예를 들어:
- `UNPATCHED_KNOWN_VULNERABILITY`와 `MISCONFIGURATION`은 서로 다른 RootCause이지만 CSF의 `PR.PS` 범주와 연결될 수 있다.
- `CREDENTIAL_OR_KEY_MISMANAGEMENT`와 `WEAK_ACCESS_CONTROL`은 서로 다른 RootCause이지만 `PR.AA` 범주와 연결될 수 있다.

## 3.2. 권장 변경안: 세 가지 분류축 분리

기존의 단일 상위 분류 체계를 다음 세 가지 독립적인 축으로 재설계한다.

### A. RootCause

실제 사건에서 확인된 구체적인 기술적 약점 또는 조직적 관리 실패를 표현한다.

예시:
- `UNPATCHED_KNOWN_VULNERABILITY`
- `CREDENTIAL_OR_KEY_MISMANAGEMENT`
- `INSUFFICIENT_ENCRYPTION`
- `WEAK_ACCESS_CONTROL`
- `INSUFFICIENT_LOGGING_AUDIT`
- `INSUFFICIENT_SECURITY_MONITORING_OPERATIONS`
- `INADEQUATE_INCIDENT_RESPONSE`
- `THIRD_PARTY_OR_SUPPLY_CHAIN_RISK`
- `MISCONFIGURATION`

### B. FailureNature

RootCause가 기술적 실패인지 조직적 절차 실패인지 등을 비교하기 위한 축이다.

| ID | 정의 |
|---|---|
| `TECHNICAL_CONTROL_FAILURE` | 기술적 보안 통제, 시스템 기능, 설정 또는 구현의 실패 |
| `ORGANIZATIONAL_PROCESS_FAILURE` | 조직의 정책, 절차, 인력, 책임체계 또는 운영상의 실패 |
| `EXTERNAL_DEPENDENCY_FAILURE` | 외부 공급자, 협력사 또는 공급망에 대한 관리·통제 실패 |

한 사건에서 서로 다른 성격의 실패가 확인되면 각각 별도로 기록한다.

### C. ControlDomain

실패한 보안 통제의 업무 영역을 나타낸다.

예시:
- `VULNERABILITY_MANAGEMENT`
- `IDENTITY_AND_ACCESS_MANAGEMENT`
- `DATA_PROTECTION`
- `SECURITY_MONITORING`
- `INCIDENT_RESPONSE`
- `SUPPLY_CHAIN_SECURITY`
- `CONFIGURATION_MANAGEMENT`

ControlDomain은 프로젝트 내부의 분석·집계 기준이며, NIST CSF 카테고리와 동일한 개념으로 취급하지 않는다.

## 3.3. 분석 시 우선순위

- 사건 간 구체적인 원인 비교: RootCause
- 기술적 실패와 조직적 실패의 비율 비교: FailureNature
- 보안 통제 영역별 비교: ControlDomain
- 공식 보안 프레임워크와의 연계: NIST CSF 및 NIST SP 800-53 매핑

기존 5개 상위 분류는 핵심 비교 기준에서 제외하고, 필요하다면 화면 표시용 그룹(`display_group`)으로만 유지한다.

# 4. Q3. NIST 매핑 체계와 확정 절차

## 4.1. 표준별 역할 분리

각 표준의 역할을 다음과 같이 구분한다.

| 표준 | 역할 |
|---|---|
| CWE | 소프트웨어 및 시스템의 기술적 약점 분류 |
| NIST CSF 2.0 | 조직의 사이버보안 위험관리 성과 및 통제 영역 분류 |
| NIST SP 800-53 Rev.5 | 구체적인 보안·개인정보 보호 통제 카탈로그 |
| NIST SP 800-61 Rev.3 | 사이버보안 사고 대응 지침 |
| MITRE ATT&CK | 공격자의 실제 행동 및 공격 기법 분류 |

조직적 관리 실패를 CWE에 억지로 매핑하지 않는다.

CWE는 기술적 약점을 설명하는 데 사용하고, 조직의 통제·절차 실패는 NIST CSF 및 SP 800-53을 중심으로 표현한다.

| `CREDENTIAL_OR_KEY_MISMANAGEMENT` | `IA-5`, `AC-2`, `AC-6` |
| `INSUFFICIENT_ENCRYPTION` | `SC-8`, `SC-13`, `SC-28` |
| `WEAK_ACCESS_CONTROL` | `AC-2`, `AC-3`, `AC-6` |
| `INSUFFICIENT_LOGGING_AUDIT` | `AU-2`, `AU-3`, `AU-12` |
| `INSUFFICIENT_SECURITY_MONITORING_OPERATIONS` | `SI-4`, `CA-7`, `AU-6` |
| `INADEQUATE_INCIDENT_RESPONSE` | `IR-4`, `IR-5`, `IR-6`, `IR-8` |
| `THIRD_PARTY_OR_SUPPLY_CHAIN_RISK` | `SR-3`, `SR-5`, `SR-6`, `SA-9` |
| `MISCONFIGURATION` | `CM-2`, `CM-3`, `CM-6`, `CM-7` |

**중요:** 위 매핑은 후보이다. 공식 문서에 통제 ID가 존재한다는 것과 해당 RootCause에 적합한 매핑이라는 것은 별개다.

또한 공식 버전별 통제 내용 및 식별자 변경 여부를 검증해야 한다.

## 4.5. NIST 매핑 확정 절차

다음 절차를 거친 경우에만 확정 매핑으로 저장한다.

1. NIST 공식 CSF 2.0 JSON 또는 Excel에서 세부 범주 ID와 설명을 확인한다.
2. NIST 공식 SP 800-53 Release 5.2.0 자료에서 개별 통제 ID와 설명을 확인한다.
3. RootCause 정의와 통제의 목적·범위가 일치하는지 검토한다.
4. 실제 사건의 출처가 해당 통제 실패를 뒷받침하는지 검토한다.
5. 분석가의 검토 및 승인을 거친다.

권장 저장 구조:

```json
{
  "root_cause": "INSUFFICIENT_LOGGING_AUDIT",
  "standard": "NIST_SP_800_53",
  "standard_version": "5.2.0",
  "control_id": "AU-2",
  "mapping_status": "candidate",
  "mapping_rationale": "필요한 보안 이벤트가 감사 대상으로 정의되지 않음",
  "evidence_ref": "source_001",
  "review_status": "pending"
}
```

`mapping_status`와 `review_status`는 서로 다른 필드로 관리한다.

예시 상태:
- `candidate`: 검토 후보
- `confirmed`: 전문가 검토 완료
- `rejected`: 부적절한 매핑으로 기각

공식 ID 존재 여부, RootCause와의 의미적 적합성, 사건 증거의 충분성은 각각 별도로 검증한다.

# 5. Q4. VERIS의 Former Employee 분류

## 5.1. 검토 결과

VERIS 공식 Actors 문서에서는 former employees를 External actor의 사례로 포함하고 있다.

또한 `actor.external.variety`에 `Former employee`가 별도 세부 유형으로 존재한다.

따라서 VERIS와의 상호운용성을 위해 프로젝트 내부의 `FORMER_INSIDER`를 VERIS의 `External / Former employee`로 변환하는 대응 관계는 유지한다.

## 5.2. 프로젝트 내부 분류 유지

기존 ActorOrigin 네 가지는 그대로 유지한다.

| 프로젝트 분류 | 정의 | VERIS 대응 |
|---|---|---|
| `INTERNAL` | 공격 시점에 피해 조직의 직원 또는 계약자 신분인 행위자 | Internal |
| `FORMER_INSIDER` | 공격 시점에는 퇴직·계약 종료 상태이며 과거 조직 관계에서 취득한 권한·정보·접근 수단을 이용한 행위자 | External / Former employee |
| `PARTNER` | 협력사·공급사 등 외부 조직과의 정당한 업무 관계를 통해 접근한 행위자 | Partner |
| `EXTERNAL` | 피해 조직과 직접적인 정당한 업무 관계가 없는 행위자 | External |

## 5.3. 주의할 경계 사례

협력사 직원 계정이 도용되어 침입한 사례를 무조건 `PARTNER`로 분류하면 안 된다.

- 협력사 직원 본인이 공격했다면 `PARTNER`
- 외부 공격자가 협력사 직원 계정을 탈취했다면 `EXTERNAL` 또는 행위자 유형 미확인

공격자 신원과 계정 소유자는 별도 개념으로 관리한다.

또한 과거에 해당 조직에서 근무했다는 사실만으로 `FORMER_INSIDER`를 부여하지 않는다. 과거 조직 관계와 공격의 연관성이 확인되어야 한다.

행위자의 고용 상태나 조직적 관계가 확인되지 않았다면 추측하지 않는다.

# 6. Q5. MITRE ATT&CK 하위 기법 유지 기준

## 6.1. 검토 결과

하위 기법은 상위 기법보다 구체적인 공격 행동을 나타낸다.

따라서 문서에 상위 기법의 일반적인 행동만 확인되는 경우에는 상위 기법까지만 매핑한다.

하위 기법을 선택하려면 해당 하위 기법을 다른 하위 기법과 구별할 수 있는 구체적인 행동이 출처에서 확인되어야 한다.

하위 기법별로 모든 상황에 적용할 수 있는 단일한 필수 조건 목록이 있는 것으로 가정하지 않는다. 각 기법의 공식 설명과 절차(Procedure Examples), 관련 데이터 소스 등을 참조하여 개별적으로 판단한다.

## 6.2. specific_evidence 작성 원칙

다음 문장을 매핑 지침으로 사용한다.

"출처에서 하위 기법을 구별하는 구체적인 공격 대상·수행 방식·접근 경로 중 해당 하위 기법의 정의에 부합하는 행동이 직접 확인될 때만 하위 기법을 선택하고, 구별 근거가 부족하면 상위 기법까지만 매핑한다."

## 6.3. 사례

예시: `T1003 – OS Credential Dumping`

| 출처의 설명 | 매핑 |
|---|---|
| 공격자가 자격 증명을 덤프했다 | `T1003` |
| 공격자가 LSASS 메모리에 접근하여 자격 증명을 추출했다 | `T1003.001` |
| 공격자가 SAM 데이터베이스에서 자격 증명을 추출했다 | `T1003.002` |

악성코드가 특정 하위 기법을 사용할 수 있다는 정보만으로 해당 사건에서 실제로 그 기법이 실행되었다고 판단하지 않는다.

## 6.4. 코드 및 데이터 구조 개선

기존 `specific=True/False`만으로 하위 기법을 선택하는 구조는 근거를 충분히 보존하지 못한다.

다음 필드를 추가한다.

```json
{
  "technique_id": "T1003.001",
  "parent_technique_id": "T1003",
  "specific_evidence": "출처에서 LSASS 메모리에 접근하여 자격 증명을 추출했다고 명시함",
  "evidence_quote": "LSASS memory was accessed to extract credentials",
  "evidence_strength": "direct",
  "review_status": "human_confirmed"
}
```

필드의 역할:
- `technique_id`: 선택한 ATT&CK 기법
- `parent_technique_id`: 상위 기법
- `specific_evidence`: 하위 기법을 선택한 이유
- `evidence_quote`: 원문에서 확인한 근거 문장
- `evidence_strength`: 근거의 직접성
- `review_status`: 사람 검토 결과

# 7. 기존 B1~B5 설계에 대한 통합 반영 사항

## B1. RootCause 시드

기존 8개 시드의 기본 방향은 유지한다.

다만 다음 변경을 반영한다.

1. `INSUFFICIENT_MONITORING_DETECTION`을 `INSUFFICIENT_LOGGING_AUDIT`와 `INSUFFICIENT_SECURITY_MONITORING_OPERATIONS`로 분리한다.
2. 기존 RootCause와 신규 RootCause의 경계 규칙을 문서화한다.
3. 기술적 약점과 조직적 관리 실패가 한 사건에 함께 나타나면 각각 기록한다.
4. 피해 결과만으로 원인을 추정하지 않는다.
5. 추가 RootCause는 파일럿에서 `other` 및 분류 불가 사례를 수집하고 독립적인 원인 유형인지 검증한 후 도입한다.

## B2. CWE 및 NIST 표준

1. CWE는 기술적 약점 분류에 사용한다.
2. NIST CSF는 조직의 사이버보안 위험관리 성과 영역을 표현한다.
3. NIST SP 800-53은 구체적인 보안 통제와 연결한다.
4. 조직적 절차 실패를 CWE에 억지로 매핑하지 않는다.
5. NIST 매핑은 공식 자료를 통한 ID 검증, 의미 검토, 사건 증거 확인, 사람 승인을 거친다.
6. 공식 ID 존재 여부와 RootCause와의 적합성을 별도 관리한다.

## B3. ActorOrigin

1. 기존 네 가지 분류를 유지한다.
2. `FORMER_INSIDER`는 프로젝트 내부에서 독립적으로 유지한다.
3. VERIS 대응 시 `External / Former employee`로 변환한다.
4. 공격자와 계정 소유자를 구분한다.
5. 전직자 또는 협력사 직원이라는 신분만으로 행위자 유형을 추측하지 않는다.

## B4. 질문 틀

기존 (a), (b), (c) 구조를 유지한다.

- (a) 악용된 취약점
- (b) 기술적 약점 및 조직적 관리 실패
- (c) 실제 공격 행동 및 ATT&CK 기법

RootCause, FailureNature, ControlDomain은 서로 다른 분석 속성으로 분리한다.

## B5. ATT&CK 매핑

1. AttackBehavior 서술을 먼저 보존한다.
2. AI는 ATT&CK 후보를 제안한다.
3. 사람은 후보의 적합성을 검토하고 승인한다.
4. AI 제안은 사람 확인 전 확정 집계하지 않는다.
5. 하위 기법은 구별 가능한 구체적인 공격 행동이 직접 확인되는 경우에만 유지한다.
6. 문서 직접 언급, 사람 검증, 악성코드 기반 유도 결과를 구분한다.
7. ATT&CK 버전과 매핑 이력을 기록한다.

# 8. 추가로 유지해야 할 데이터 품질 원칙

## 8.1. 근거 및 확정 상태 분리

문서에서 특정 ATT&CK 기법을 직접 언급했다고 실제 공격에 사용된 사실이 확정되는 것은 아니다.

따라서 다음 개념을 분리한다.

- `evidence_strength`: 근거가 얼마나 직접적인가
- `assertion_status`: 출처가 해당 사실을 확정·주장·추론 중 어떤 수준으로 표현하는가
- `review_status`: 분석가가 검토했는가
- `mapping_status`: 표준 매핑이 승인되었는가

AI confidence와 evidence strength도 같은 의미로 취급하지 않는다.

## 8.2. ATT&CK 매핑 상태

권장 상태:

| 상태 | 의미 | 확정 집계 |
|---|---|---|
| `ai_suggested` | AI가 제안한 후보 | 제외 |
| `human_confirmed` | 사람이 검토하고 승인 | 포함 가능 |
| `human_rejected` | 사람이 기각 | 제외 |
| `no_match` | 적합한 ATT&CK 기법 없음 | 제외 |
| `documented` | 출처에 직접 기법이 언급됨 | assertion_status에 따라 판단 |
| `backbone_derived` | 악성코드-기법 관계에서 유도됨 | 별도 집계 |

`documented`와 `human_confirmed`는 서로 다른 축이다. 문서 직접 언급과 사람 검토 결과를 하나의 상태로 합치지 않는다.

## 8.3. 다중 출처 보존

동일한 기법이 여러 출처에서 서로 다른 확정 수준으로 등장하면 출처별 주장을 각각 보존한다.

최초 입력된 기록만 남기는 방식으로 정보를 손실하지 않도록 한다.

## 8.4. 인과관계 구분

취약점, RootCause, AttackBehavior 간 관계를 자동으로 인과관계라고 단정하지 않는다.

출처에서 직접 확인된 관계와 분석가의 추론 관계를 구분한다.

# 10. 최종 설계 원칙

프로젝트의 전체 구조는 다음 원칙을 따른다.

1. Vulnerability는 공격에 악용된 기술적 결함을 나타낸다.
2. RootCause는 공격을 가능하게 하거나 피해를 확대시킨 기술적·조직적 통제 실패를 나타낸다.
3. FailureNature는 RootCause의 실패 성격을 비교하기 위한 독립적인 분류축이다.
4. ControlDomain은 실패한 보안 통제의 업무 영역을 나타낸다.
5. NIST CSF와 SP 800-53은 RootCause와 관련된 통제 영역을 표준화하는 데 사용한다.
6. AttackBehavior는 출처에서 확인된 실제 공격 행동을 보존한다.
7. ATT&CK Technique는 AttackBehavior를 표준화하여 사건 간 공격 패턴을 비교하는 데 사용한다.
8. AI 제안과 사람 검증 결과를 구분한다.
9. 출처에 없는 사실과 확인되지 않은 인과관계는 추측하지 않는다.
10. 사건에 대한 원인 분류와 표준 매핑은 근거를 보존하고 재검토할 수 있어야 한다.

프로젝트의 차별점은 뉴스에서 CVE나 ATT&CK ID를 추출하는 데 그치지 않고, 실제 침해사고의 기술적 취약점, 조직적 관리 실패, 공격자의 행동을 연결하여 사건 간 공통 원인과 공격 패턴을 분석하는 데 있다.

기존 데이터 모델을 전면 교체하기보다는 현재 구조를 유지하면서 RootCause의 의미와 분류축을 먼저 명확히 하고, 이후 NIST 및 ATT&CK 매핑의 검증 체계를 보완하는 순서로 개발한다.

# 11. 후속 AI에게 요청할 작업

위 검토 결과를 기존 B1~B5 설계 문서와 코드에 반영하기 전에 다음 작업을 수행하라.

1. 기존 B1~B5의 내용을 확인하고 위 검토 의견과 비교하라.
2. 기존 설계 중 유지할 부분, 수정할 부분, 삭제할 부분을 구분하라.
3. RootCause 시드 변경 전후의 매핑표를 작성하라.
4. `FailureNature`와 `ControlDomain`의 정의 및 분류 규칙을 구체화하라.
5. 기존 데이터와 코드에서 영향을 받는 부분을 식별하라.
6. NIST 매핑 후보는 공식 원본 파일을 기준으로 ID 존재 여부와 설명을 검증하라. 검증할 수 없는 항목은 확정하지 말고 후보로 남겨라.
7. ATT&CK 매핑 코드에서 근거 및 검토 상태를 보존하도록 수정안을 제시하라.
8. 기존 데이터의 마이그레이션 방안을 제시하라.
9. 변경 사항을 실제로 반영하기 전에 설계상 충돌, 중복 집계, 정보 손실 가능성을 먼저 보고하라.

특히 검토 의견을 무조건 수용하지 말고 기존 설계와의 정합성, 실제 데이터 적용 가능성, 분석 목적에 부합하는지를 기준으로 재검토하라.

**중요:** 기존 파일이나 코드에 없는 기능이 이미 구현되어 있다고 가정하지 말고, 실제 확인된 내용과 제안 사항을 구분하라.
````

**답변 요약**: 요청한 9개 항목 순서로 반영 전 점검을 보고했다. 방향은 수용하고, 모니터링 시드는 대체하지 않고 계층으로 분리, `FailureNature`와 `ControlDomain`은 독립 축이 아니라 시드에서 파생하는 속성으로 저장, NIST 후보는 공식 파일 검증 뒤로 보류하자고 수정 제안했다.

**답변 요약**: Gemini 키는 무료로 받을 수 있지만 무료 등급에는 한도가 있다고 답했다. 공식 페이지에서 모델마다 무료 여부가 다르고 현재 요청 한도의 정확한 숫자는 확인하지 못했다고 밝혔다. 22건 문서를 문서당 여러 번 호출하면 한도에 걸릴 수 있어 Claude로 바꾸는 것을 추천했다.


## 48. 사용자 입력

````text
Claude로 바꾸는 걸로 하고 1~3단계 시작해줘
````

**답변 요약**: LLM을 Claude로 정하고 1~3단계를 했다. `security_kg/pipeline/`에 원본 10개 파일 복사본(`_original_climatekg/`), Claude 호출부(`llm.py`), 모델, 프롬프트, 적합성 검사(근거 문장이 원문에 있는지 포함), 문서 텍스트 추출, 추출 에이전트를 만들고 가짜 응답으로 시험했다. 실제 LLM으로는 실행하지 않았다.


## 49. 사용자 입력

````text
임베딩 모델 제안해줘
````

**답변 요약**: 원본의 NV-Embed-v2(7B, GPU 필요, 영어 중심)는 맞지 않다고 하고 BAAI/bge-m3를 추천했다. 연결 순서(정확 일치와 별칭 사전, 임베딩 후보, Claude 판정, 사람 확인)와 임계값 재조정, 시험 자료, 네트워크 접근 필요를 알렸다. 모델 사양은 제가 아는 범위이고 직접 확인하지 못했다고 밝혔다.


## 50. 사용자 입력

````text
bge-m3로 진행하고 시험부터 해줘
````

**답변 요약**: Hugging Face 주소가 막혀 있어 환경 허용 목록에 추가하는 승인을 두 번 요청하고(huggingface.co와 CDN 주소 7개) bge-m3를 받아 시험했다. 질의 35개 중 1위 정답 21개(60%), 3위 안 29개(83%). 이름과 음역은 잘 맞았고 서술형은 약했다. 점수로 맞고 틀림을 가를 수 없어(부정 예도 0.56~0.65) 임계값 자동 합치기는 쓰지 않고 임베딩을 후보 찾기에만 쓰자고 제안했다. 정답 라벨은 별칭 검토표 4행을 빼고 제가 썼고 사람이 확인하지 않았다.


## 51. 사용자 입력

````text
11/27 대화기록 md문서로 만들어줘
````

**답변 요약**: 이 문서를 만들었다.
